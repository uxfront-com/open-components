Selects let people choose one option out of a list, like their country, a time zone or how to sort a page. They're so common that they're often rebuilt from scratch to look a bit nicer, and that's where they go wrong. Think of a dropdown made of `<div>`s that keyboard users can't open, a "Choose a country" that stands in for the label and disappears once someone chooses, or a sort order that reloads the page as soon as the arrow keys move past the first option.

This page walks you through building one the right way. We'll look at:
- **User Interface** (UI) - how a select looks
- **User Experience** (UX) - how it behaves for every person and every input
- **Developer Experience** (DX) - how developers work with it
- **Agentic Experience** (AX) - how agents can read and verify it

Every example on this page runs on our [reference implementation](/docs/components/select#reference-implementation), which does its part of every rule in the [checklist](/docs/components/select#checklist), so feel free to open them as you read. The code under each example comes in React, Vue, Svelte, Angular, Solid, Astro and Vanilla, written for a Select with the same API in each. Pick yours from the Framework select above the sidebar. Vanilla is plain HTML and JavaScript, so it writes out the markup from the [DOM contract](/docs/components/select#deterministic).

The Select wraps the browser's own `<select>`, rather than rebuilding one. That way, phones show their own picker, autofill and forms work as they always do, and it all works before your JavaScript loads. Like the [Input](/docs/components/input), its label, hint and error message are elements of their own, which you link to it by ID, until the Field on our [Roadmap](/docs/getting-started/roadmap) puts them together for you.

## At a glance

| Aspect   | Select                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------- |
| Element  | `<select>`, inside a `<div>` that draws the field, with an indicator after it                   |
| Role     | `combobox`, with an `option` for each choice                                                    |
| Name     | Its `<label>`, linked with `for`, and never its placeholder                                     |
| Keyboard | The browser's own: `Tab` to it, then keys to open it, move through its options and type ahead   |
| States   | Hover, focus, disabled and invalid                                                              |
| Options  | `<option>` and `<optgroup>` elements, between its tags                                          |
| Sizes    | `xs`, `sm`, `md`, `lg` and `xl`, with the same heights as the Input and the Button              |
| Pattern  | A native [`<select>`](https://html.spec.whatwg.org/multipage/form-elements.html#the-select-element), rather than the APG's select-only combobox, which rebuilds one with ARIA |
| WCAG 2.2 | 1.3.1, 1.3.5, 1.4.3, 1.4.11, 2.1.1, 2.4.7, 2.5.8, 3.2.2, 3.3.1, 3.3.2 and 4.1.2, among others   |

## User Interface (UI)

Let's start with how a select looks: its parts, its options, its sizes, how it shows each of its states, how wide it should be and what browsers that can style the picker add.

### Anatomy

::select-anatomy
1. **Container** — The root `<div>`, which draws the border and carries the size.
2. **Control** — The `<select>` itself, which shows the chosen option and takes focus. Its label names it.
3. **Indicator** — The chevron that says the field opens, hidden from assistive technologies.
4. **Focus ring** — An outline around the whole field, drawn outside it so nothing moves.
::

Every select has all four. The picker, the list that opens, is drawn by the browser, or by the phone, which is why it isn't one of the parts. The label, any hint and any error message sit outside the Select, in the page, and point to the control by its `id` (see [Label every select](/docs/components/select#label-every-select)). The parts always render in the same order, which you can see in the [DOM contract](/docs/components/select#deterministic).

### Options

The options go between the Select's tags, as `<option>` elements, which you can put in groups with `<optgroup>`. Each option has a `value`, which is what its form sends, and text, which is what people see. Mark the one people start on with `selected`, or the select starts on the first.

::

- Keep options to plain text. Screen readers read an option's text, and only its text, and type-ahead jumps to an option by the letters it starts with. An icon, a flag or a second line in an option only shows in some browsers, and never reaches screen readers, so if your options need more than words, a Combobox, on our [Roadmap](/docs/getting-started/roadmap), is a better fit.
- Put options in an order people can predict, like alphabetical for countries or by size for sizes, so they can find one without reading the whole list.
- Groups get their name from `label`, which screen readers can announce as people move into a group. A group can't be chosen itself, and it can't hold another group.
- Values are strings, since that's what a form sends. If yours are numbers or objects, look them up by their value when the form is sent.

### Placeholder

When there's no sensible option to start on, like a country, the `placeholder` prop adds an empty first option, with a value of `""`, which says what to do, as in "Choose a country". HTML calls it the [placeholder label option](https://html.spec.whatwg.org/multipage/form-elements.html#placeholder-label-option). With `required`, the form won't count it as an answer, so people can't send it without choosing.

A placeholder isn't a label. It goes away once people choose, so they can't check what they were asked for, and screen readers read it as the select's value rather than its name. Keep a visible label, and use the placeholder to say what to do. Where one option is the right answer for most people, like the language of the page, start on that option instead, which saves them a step.

### Sizes

The `size` prop scales the height, text, indicator, padding and corner radius together, and `md` is the default. The heights are the same as the [Input](/docs/components/input#sizes)'s and the [Button](/docs/components/button#sizes)'s, so a select, an input and a button of the same size line up in a row.

| Size | Min. height | Text | Indicator | Padding | Gap | Radius |
| ---- | ----------- | ---- | --------- | ------- | --- | ------ |
| `xs` | 24px        | 12px | 14px      | 8px     | 4px | 6px    |
| `sm` | 32px        | 14px | 16px      | 10px    | 8px | 6px    |
| `md` | 36px        | 14px | 16px      | 12px    | 8px | 8px    |
| `lg` | 40px        | 16px | 20px      | 14px    | 8px | 8px    |
| `xl` | 48px        | 16px | 20px      | 16px    | 8px | 12px   |

Sizes are set in `rem`, and the table shows the values we recommend at the default text size of 16px. Every size meets the 24 × 24px minimum from [WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). On touch screens, the select gets two things on top of that, as the Input does. Its text grows to at least 16px, since Safari on iOS zooms in on a select with smaller text as soon as it gets focus, and its hit area grows to at least 44px tall, without the field looking any bigger.

The native `<select>` has a `size` attribute of its own, which turns it into a list that's always open. The Select's `size` prop takes its place, so a Select is always one line tall. A list that stays open is a different component, like a Radio Group or a Listbox.

| State     | Selector                                       | Recommended look                                         |
| --------- | ---------------------------------------------- | -------------------------------------------------------- |
| Hover     | `:hover`, inside `@media (hover: hover)`       | The border at 80% of the text colour, up from 55%        |
| Focus     | `:has(> select:focus-visible)`                 | A 2px outline, 2px from the edge, in `--color--focus`    |
| Disabled  | `:has(> select:disabled)`                      | 50% opacity and a `not-allowed` cursor                   |
| Invalid   | `:has(> select[aria-invalid="true"])`          | A 2px border in `--color--error-text`                    |

The field is drawn by the root, so it reads each state from the `<select>` inside it, with `:has()`. As on the Input, we recommend leaving `:invalid` and `:user-invalid` out of it: `:invalid` matches a required select on its placeholder before anyone has chosen anything. The invalid look comes from `aria-invalid` instead, which you set when the error message shows.

There's no read-only state, since HTML doesn't have one for a `<select>`. You'll find what to do instead in the [FAQ](/docs/components/select#faq). None of the states change the select's size or position: the invalid border's second pixel is drawn inside the field, and the focus ring outside it.

### Width and layout

The Select fills the width it's given, like the Input, which is why it doesn't have a prop for it. We recommend sizing it to its longest option, since a field that's much wider than its answers looks like it wants more. You can set the width from a class, in `ch`, with room for the padding and the indicator.

::select-widths-example
::framework-switcher

### The picker

The list that opens is the browser's own, and on phones and tablets it's the system's, which is built for a thumb. Browsers that support `appearance: base-select` let a page style it too, along with its options. We use it as an enhancement, which means the Select works and looks finished without it, and the picker takes the field's tokens in browsers that have it.

As we checked on 11 October 2026, `appearance: base-select` works in Chrome and Edge 135 and later, and in Safari 27 and later, on macOS and iOS. Firefox only has it behind a setting, since version 149. You'll find the latest in [Can I use](https://caniuse.com/mdn-css_properties_appearance_base-select) and [MDN's browser compatibility data](https://github.com/mdn/browser-compat-data). Here's how we use it:

- Every style for it goes inside `@supports (appearance: base-select)`, so browsers without it never see half of it.
- We only turn it on for fine pointers, like a mouse (`@media (pointer: fine)`), so phones and tablets keep their own picker.
- Where the picker is styled, the browser draws an arrow of its own, `::picker-icon`, so the Select hides it and keeps its indicator, rather than showing two, which also keeps the chevron the same in every browser.
- The styled picker is never wider than the screen, so a long option wraps onto another line rather than running off the edge ([WCAG 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)).
- The enhancement doesn't change the markup. We leave out the newer `<button>` and `<selectedcontent>` inside the select, since browsers without `base-select` would show the button as stray text.

### Tokens

The select reads three [theme tokens](/docs/foundations/design-tokens#theme-tokens), which every component shares:

| Token                   | Used for                                                                            |
| ----------------------- | ----------------------------------------------------------------------------------- |
| `--color--neutral-text` | The chosen option and the options in a styled picker, and mixed into the border     |
| `--color--error-text`   | The border of an invalid select                                                     |
| `--color--focus`        | The focus ring, which is the same for every component                               |

The border is mixed from the text colour, as the Input's is: 55%, which needs 3:1 against the page, and 80% on hover. With our reference tokens, from the Tailwind CSS palette, the border comes to 3.5:1 on white and 5.0:1 on zinc-900. A styled picker sits on `Canvas`, the system's own background colour, which follows `color-scheme` and forced colours. You'll find the tokens themselves in the Button's [`tokens.css`](/docs/components/button#reference-implementation), which you can copy into your theme.

If you need to tune a select, you can set its [own variables](/docs/foundations/design-tokens#component-variables), such as `--select--height`, `--select--radius` or `--select--border-color`, from a class. The Select's styles sit in the `components` cascade layer, so your class wins without any specificity tricks:

## User Experience (UX)

Now let's look at how a select behaves for every person, input and setting. A good select is [accessible](/docs/components/select#accessible), [predictable](/docs/components/select#predictable), designed in [every state](/docs/components/select#every-state) and [adaptive](/docs/components/select#adaptive).

### Accessible

#### Use the native element

A native `<select>` gives you a role, a name, a value, keyboard support, type-ahead, the phone's own picker, autofill, form submission and reset, all for free, and it works before your JavaScript loads. A select rebuilt from `<div>`s with ARIA, which the APG calls a [select-only combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/examples/combobox-select-only/), only gets what you build: every key, the focus inside the list, scrolling, positioning near the edge of the screen and the announcements, each tested in every screen reader by hand.

#### Label every select

The label is also the select's accessible name. Screen readers read it when the select gets focus, voice control users say it out loud ("click Country"), and tests and agents use it to find the select. The [Placeholder](/docs/components/select#placeholder) example above shows a select with its label and its hint, which follow these rules:

- Every select has a visible `<label>`, linked to it with `for` and the select's `id` ([WCAG 1.3.1](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html), [3.3.2](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)). Clicking the label focuses the select, which makes for a bigger target.
- A hint, like why you're asking, goes in the select's description, which screen readers read after its name and its value. You can do that with `aria-describedby`, pointing at the hint's `id`.
- If you name a select with `aria-label` or `aria-labelledby`, make sure the name includes the visible label, ideally at the start ([WCAG 2.5.3](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html)).
- The Select doesn't make up IDs of its own (see [Deterministic](/docs/components/select#deterministic)), so give it an `id` for its label to point at, and one to each hint and error message that points back at it.

#### Contrast and size

- The chosen option needs a contrast of at least 4.5:1 with its background, and so do the options in a picker you style ([WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)). Disabled selects are exempt, but they should still be readable.
- The border needs 3:1 against the page ([WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)), since it's how people see that there's a field there at all. The focus ring needs 3:1 as well.
- Every select is at least 24px tall ([WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). On touch screens, the hit area grows to 44px tall ([WCAG 2.5.5](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)). The indicator lets presses through (`pointer-events: none`), so pressing it opens the picker, like pressing anywhere else on the field.

#### Show focus

When a select has focus, the whole field shows an outline in the same focus colour as every other component ([WCAG 2.4.7](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)). It's drawn by the root, so it goes around the indicator too, and like the Input's, it's at least 2px thick and drawn outside the border, and we recommend 2px for both. You'll also want to keep a focused select clear of sticky headers and footers, which you can do with `scroll-padding` ([WCAG 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)).

### Predictable

#### Keyboard

The keys are the browser's own, so they're the ones people already know from every other select on their system:

| Key                         | Select                                                                              |
| --------------------------- | ----------------------------------------------------------------------------------- |
| `Tab`, `Shift+Tab`          | Moves focus to and from the select                                                  |
| `Space`, or `Alt+↓` on Windows | Opens the picker, though the keys differ between systems and browsers            |
| `↑`, `↓`                    | Move through the options. On Windows, with the picker closed, they choose straight away |
| Letters                     | Jump to the first option that starts with what you type                             |
| `Enter`                     | Chooses the highlighted option and closes the picker                                |
| `Escape`                    | Closes the picker without choosing                                                  |

Unlike the Input, a select doesn't submit its form on `Enter`, since HTML's implicit submission only comes from text fields. That's one more reason to give every form a submit button.

#### Don't act on change

Choosing an option only changes the value. It never submits the form, goes to another page or moves focus, so people can look through the options without anything happening behind their backs ([WCAG 3.2.2](https://www.w3.org/WAI/WCAG22/Understanding/on-input.html)). That matters most on Windows, where the arrow keys choose the next option while the picker is closed, and `change` fires on every press. A "Go to" select that loads a page on `change` sends keyboard users to the second option before they've seen the third.

If a choice should do something, like sort a list or change the language, put a Button next to the select, as in "Apply". If the effect is small and stays on the page, like re-sorting a table in place, it's fine to apply it right away, as long as focus stays on the select and nothing moves above it. You can tell people what changed with a status message.

#### Help people choose

- Give each select that asks about the person filling in the form the matching `autocomplete` value, like `country`, `honorific-prefix` or `cc-exp-month` ([WCAG 1.3.5](https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html)), so browsers can choose it for them. `country` matches an option by its value, as a country code, and `country-name` by its text.
- Start on the option most people want, if there is one, and on a [placeholder](/docs/components/select#placeholder) if there isn't, rather than on whichever option happens to be first, which people may send without noticing.
- Keep the list short enough to scan. With a few options that fit on the screen, a Radio Group shows them all at once, and with hundreds, a Combobox lets people type to find theirs (see [Select or something else?](/docs/components/select#select-or-something-else)).

### Every state

#### Disabled

A disabled select can't be focused, changed or submitted. `disabled` sets the native attribute, so the select leaves the tab order, screen readers announce it as dimmed or unavailable when they read through the page, and its form leaves its value out when it's sent. We recommend disabling as little as you can, since a disabled select can't explain why it's disabled, and keyboard users can't even reach it to find out. If there's only one option, show it as text instead.

#### Invalid

An invalid select has a value that needs fixing, most often a required one that's still on its placeholder, and an error message that says what to choose. The Select shows the state, and the page decides when to show it.

::select-validation-example
::framework-switcher
#react
```tsx
import { useRef, useState, type FormEvent } from "react";
import { flushSync } from "react-dom";

export function Address() {
  const [country, setCountry] = useState("");
  const [error, setError] = useState("");
  const [status, setStatus] = useState("");
  const select = useRef<HTMLSelectElement>(null);

  function update(value: string) {
    setCountry(value);
    // Once an error shows, check again as people choose, so it clears as soon as it's fixed.
    if (error) setError(validateCountry(value));
  }

  async function save(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const message = validateCountry(country);
    if (message) {
      // Focus once the error is in the page, so screen readers read it with the select.
      flushSync(() => {
        setError(message);
        setStatus("Couldn't save. Check your country.");
      });
      select.current?.focus();
      return;
    }
    await api.save(country);
    setStatus("Saved");
  }

  return (
    <form noValidate onSubmit={save}>
      <label htmlFor="country">Country</label>
      <Select
        ref={select}
        id="country"
        autoComplete="country"
        placeholder="Choose a country"
        required
        value={country}
        aria-invalid={error ? true : undefined}
        aria-describedby={error ? "country-error" : undefined}
        onChange={(event) => update(event.target.value)}
      >
        <option value="FR">France</option>
        <option value="DE">Germany</option>
      </Select>
      {error && <p id="country-error">{error}</p>}
      <Button type="submit" color="primary">Save</Button>
      <p role="status">{status}</p>
    </form>
  );
}
```

`validateCountry` stands in for your own check, which returns an error message, or an empty string once a country is chosen.

- Set `aria-invalid="true"` on the select while its error message shows, and point `aria-describedby` at the message. Screen readers then announce the select as invalid, and read the message after its name and value ([WCAG 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)).
- Say what to choose, as in "Choose the country you live in", rather than "Invalid selection" ([WCAG 3.3.3](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html)). A red border alone can't say that, and it means nothing to people who can't tell red apart ([WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)).
- Check a select when people submit, rather than when they leave it, since tabbing past a select doesn't mean they've chosen. Once an error shows, check again as they choose, and clear it as soon as the value is right.
- When a submit fails, move focus to the first invalid field, once the error is in the page, and say what happened in a status message, as on the [Input](/docs/components/input#invalid).
- Put `novalidate` on the form, so the browser's own error bubbles don't compete with yours, and keep `required` on the select, which tells screen readers that it's required.

### Adaptive

#### Pointer, touch and pen

- Hover styles only apply to pointers that can actually hover (`@media (hover: hover)`), otherwise a tap would leave the border looking hovered.
- On touch screens, the select reaches past the field to a hit area at least 44px tall, without the field looking any bigger, and its text is at least 16px, so Safari on iOS doesn't zoom in when it gets focus.
- Phones and tablets show their own picker, even in browsers that can style it, since we only turn the styled picker on for fine pointers (see [The picker](/docs/components/select#the-picker)).

#### More contrast

When someone asks for more contrast (`prefers-contrast: more`), as with Increase contrast on macOS and iOS, the border is drawn in the text colour at full strength, rather than at 55%.

#### Forced colours

Windows contrast themes replace every colour with the user's own, and drop backgrounds and shadows. The Select's border stays, the indicator is drawn in `currentColor`, so it takes the theme's text colour, focus is drawn with `outline`, and a disabled select is marked with `GrayText`. The invalid border's second pixel is a shadow, which forced colours drop, so in these themes it's the error message, in text, that tells people something's wrong.

#### Colour scheme

The tokens use `light-dark()`, which follows `color-scheme`, so the Select adapts to your light and dark themes on its own. Setting `color-scheme` on your themes also lets the browser draw its own picker to match, in light or dark.

#### Text size and spacing

Heights are minimums in `rem`, so the field grows with its text instead of clipping it, at 200% text size ([WCAG 1.4.4](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)) and with wider line, letter and word spacing ([WCAG 1.4.12](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)). The indicator's room grows with it, since it's set in `rem` too.

#### Languages and direction

The Select uses logical properties, so in right-to-left languages the indicator moves to the left of the field, and the text starts on the right. Options take the direction of the page, so translate them along with the label and the error message, and mark any option in another language with `lang`, as in a language picker that names each language in itself ([WCAG 3.1.2](https://www.w3.org/WAI/WCAG22/Understanding/language-of-parts.html)).

### Consistent

Once you've learned the [Input](/docs/components/input#consistent)'s API, you already know most of the Select's. These names mean the same thing everywhere in Open Components:

| Name          | Kind  | What it means                                                           |
| ------------- | ----- | ----------------------------------------------------------------------- |
| `size`        | Prop  | `xs`, `sm`, `md`, `lg` or `xl`, with the same heights everywhere        |
| `disabled`    | Prop  | The component can't be used                                             |
| `placeholder` | Prop  | What to do while there's no value, which never stands in for the label  |
| `value`       | Prop  | The value, which you bind the way your framework binds a form control's |

We recommend `size="md"` as the default. The Select also leaves a few things out, on purpose:

- There's no `options` prop. The options are `<option>` and `<optgroup>` elements between its tags, which keep every attribute HTML gives them, like `disabled`, `selected`, `label` and `lang`, and render on the server like any other markup. The cost is type safety: your type checker can't tell that a value matches one of the options, the way it could with an array of typed options. We think markup that works before JavaScript and reads like HTML is worth it, and you can still type your values where you build the options, as under [Type-safe](/docs/components/select#type-safe).
- There's no `multiple`. On a computer, a native multiple select is a list box that needs `Ctrl` or `Cmd` held down to choose more than one option, and a click without it clears every other choice, so for more than one choice, use a group of Checkboxes.
- There's no `variant` or `color`, for the same reasons as on the Input: an empty field needs its border, and its one coloured state, invalid, comes from `aria-invalid`.
- There's no `label`, `hint` or `error`. Each of them is an element of its own, linked by ID, which the Field on our Roadmap will render.

### Type-safe

Props, events and slots are typed, so your editor can autocomplete them and your type checker (`tsc`, `vue-tsc`, `svelte-check`, `ngc` or `astro check`) catches mistakes like `size="medium"`.

| Prop          | Type                                       | Default   | Description                                                            |
| ------------- | ------------------------------------------ | --------- | ---------------------------------------------------------------------- |
| `size`        | `"xs" \| "sm" \| "md" \| "lg" \| "xl"`     | `"md"`    | How big the select is                                                  |
| `disabled`    | `boolean`                                  | `false`   | Blocks focus, changes and submission                                   |
| `placeholder` | `string`                                   |           | The text of an empty first option, like "Choose a country"             |
| `value`       | `string`                                   |           | The chosen option's value, when you bind it. Without it, the select keeps its own |

| Event    | Payload | Description                                                                         |
| -------- | ------- | ----------------------------------------------------------------------------------- |
| `input`  | `Event` | Fires when people choose an option                                                  |
| `change` | `Event` | Fires when people choose an option, and on Windows as the arrow keys move through them |

Both come straight from the `<select>`, like every other native event, such as `focus` and `blur`, and a binding to `value` listens to them for you.

| Slot      | Description                                     |
| --------- | ----------------------------------------------- |
| `default` | The options, as `<option>` and `<optgroup>` elements |

### Composable

The Select renders two elements, so it splits what you pass between them. Classes and styles go on the root, which draws the field, so a class can set its variables and its width. Everything else lands on the `<select>`, including `id`, `name`, `autocomplete`, `required`, `form`, ARIA attributes and event listeners. A ref to the Select reaches the `<select>` too, since that's what form libraries and `focus()` need.

```html
  <button class="button" type="submit" data-variant="solid" data-color="primary" data-size="md">
    <span data-slot="label">Apply</span>
  </button>
</form>
```
::

- Its form sends the chosen option's value under the select's `name`, and leaves it out while the select is disabled.
- When its form resets, a select it holds goes back to the option marked `selected`, or to the first. The browser does that without firing `input` or `change`, so a bound value doesn't hear about it. If you bind the value, reset it in your state when the form resets, rather than relying on the browser.
- Form libraries register the `<select>` itself, through its ref or its attributes and listeners, which is why the Select puts them all on the `<select>`.

#### With other components

- The Field, on our [Roadmap](/docs/getting-started/roadmap), will render the label, hint and error message around a Select, give it an `id`, and set its `aria-describedby` and `aria-invalid` for you.
- An [Input](/docs/components/input) or a [Button](/docs/components/button) next to a select takes the same `size`, so they line up, like a country code beside a phone number, or a sort order beside "Apply".
- Components that pick from a list in other ways, like a Radio Group or a Combobox, will share the Select's sizes, states and rules for labels and errors.

### Controllable

The Select doesn't keep any state you can't reach. The value is yours to bind, or to leave to the browser, and every other state is a prop or an attribute that you control:

| State     | How you control it                                                        |
| --------- | ------------------------------------------------------------------------- |
| Value     | `value`, bound to your state, or left to the browser and its `selected` option |
| Disabled  | `disabled`                                                                 |
| Invalid   | `aria-invalid`, set while its error message shows (see [Invalid](/docs/components/select#invalid)) |
| Focus     | A ref to its `<select>`, and `focus()`                                     |

A bound value holds when the options change, like when they arrive from a request after the value: the Select chooses the bound option again once it's there. Start a bound value at a string, like `""` for the placeholder, since a value that's `undefined` counts as no binding at all. A value without a binding is the browser's, so the Select never sets it, which keeps the option marked `selected` and lets a reset bring it back.

## Agentic Experience (AX)

Finally, let's look at how agents read, fill in and check a select. They rely on the same accessibility tree as assistive technologies, and on a contract they can check the code against.

### Semantic

Agents that drive a browser, through Playwright or a browser MCP server, read the page through its accessibility tree, which is made of roles, names, values and states. This is how they see some of the examples on this page, with the chosen option as the value:

```yaml
- combobox "Language": English
- combobox "Plan" [disabled]: Team
- combobox "Country" [invalid]: Choose a country
- combobox "Time zone": London
```

A select without a label is a combobox with no name, so an agent can't tell a country from a time zone, any more than a screen reader user can. With a role and a name, an agent can find the select and choose an option, by its text or by its value:

```ts
await page.getByRole("combobox", { name: "Country" }).selectOption({ label: "France" });
```

A native select is one control, so agents choose an option in one call, and never have to open a list, wait for it and click inside it, as they would with a rebuilt one.

### Described

Here's the whole contract in one block, for agents to read before they build or review a select:

```yaml
component: Select
summary: Lets people choose one option out of a list, like a country or a time zone. It's a native select, and its label names it.
standard: https://opencomponents.dev/docs/components/select
element: select # inside a div, which draws the field and takes class and style
role: combobox
props:
  size: { type: [xs, sm, md, lg, xl], default: md }
  disabled: { type: boolean, default: false }
  placeholder: { type: string } # an empty first option, with value="". It never stands in for the label
  value: { type: string } # when it's bound. Without it, the select keeps its own
slots:
  default: The options, as option and optgroup elements.
events:
  input: Event, from the <select>. Fires when people choose an option.
  change: Event, from the <select>. Fires when people choose an option, and on Windows as the arrow keys move through them.
```

### Deterministic

The same props always render the same markup, leaving out anything your framework adds for itself, like comments or scoping attributes. For example, here's a required select with a placeholder and an error:

```html
<Select
  id="country"
  autocomplete="country"
  placeholder="Choose a country"
  required
  aria-invalid="true"
  aria-describedby="country-error"
>
  <option value="FR">France</option>
</Select>
```

And here's what it renders:

```html
<div class="select" data-size="md">
  <select
    data-slot="control"
    id="country"
    autocomplete="country"
    required
    aria-invalid="true"
    aria-describedby="country-error"
  >
    <option value="">Choose a country</option>
    <option value="FR">France</option>
  </select>
  <span data-slot="indicator" aria-hidden="true">
    <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round">
      <path d="m6 9 6 6 6-6" />
    </svg>
  </span>
</div>
```

- The size is mirrored as `data-size`, which is always there.
- Parts are marked with `data-slot` and always come in the same order: `control`, then `indicator`. Both are always there.
- The placeholder is always the first option, with a value of `""`, before the options you pass.
- States change attributes, never elements. The `<select>` is never replaced, so focus, the chosen option and the screen reader's position all survive every state change, an error included.
- There's nothing random or generated, like IDs or timestamps, so the markup is the same on the server, on the client and in every snapshot. You give the select its `id`, which the Field will do for you.

## Checklist

Here's every rule in one place, along with where it comes from and how to check it. A select meets the standard when it meets every **must**, and each **should** is expected unless you have a good reason not to follow it.

The scope says who meets a rule. **Component** rules are met by the Select itself, so they're the ones to check when you build or review one. **Usage** rules are met by the forms that use it, like giving every select a label, so they're the ones to check when you review a screen. **Both** rules need the two to work together, like an invalid select: the Select looks invalid from `aria-invalid`, as long as you set it when the error message shows.

The basis says where a rule comes from. About half the rules rest on **WCAG** 2.2, which we follow at level AA, and name the success criteria behind them, and a few come from **HTML**. The rest are **Open Components** rules, which are our own, like keeping phones on their own picker. Where a rule goes further than WCAG asks at level AA, its basis says so: some come from level **AAA**, like the 44px hit area on touch screens, and a rule that asks for more than its criterion says **beyond**, like using a native `<select>`, where WCAG would let you rebuild one with ARIA.

## Reference implementation

Our Vue 3 reference implementation does its part of every rule on this page, and powers every example on it. Feel free to copy it into your design system and change how it looks, but try to keep how it behaves. It reads the same theme tokens as the Button, so copy [`tokens.css`](/docs/components/button#reference-implementation) from the Button's reference implementation into your theme too.

The tests are in `Select.test.ts`. To run them, you'll need [Vitest](https://vitest.dev), set to `environment: "jsdom"` and `globals: true`, along with `@testing-library/vue`, `@testing-library/user-event` and `@testing-library/jest-dom`.

::code-collapse
:::code-group
```vue [Select.vue]
<script setup lang="ts">
import { getCurrentInstance, onMounted, useAttrs, useTemplateRef } from "vue";

export interface SelectProps {
  size?: "xs" | "sm" | "md" | "lg" | "xl";
  disabled?: boolean;
  /** The text of an empty first option, like "Choose a country". With `required`, choosing it fails validation. It never stands in for the label. */
  placeholder?: string;
}

// Attributes go on the <select> rather than on the root, so they're declared below.
defineOptions({ inheritAttrs: false });

const { size = "md", disabled = false, placeholder } = defineProps<SelectProps>();

/** The value of the chosen option, which `v-model` binds. Without it, the select keeps its own, and its form submits and resets it. */
const model = defineModel<string>();

defineSlots<{
  /** The options, as <option> and <optgroup> elements. */
  default?: () => unknown;
}>();

const attrs = useAttrs();
// Classes and styles go on the root, so a class can set its variables. Everything else
// goes on the <select>: `id`, `name`, `autocomplete`, `required`, ARIA and listeners.
// Attrs aren't reactive, so these run on every render.
const onRoot = (key: string) => key === "class" || key === "style";
const rootAttrs = () => Object.fromEntries(Object.entries(attrs).filter(([key]) => onRoot(key)));

// Whether the parent binds the value. Without a binding, defineModel would keep a copy of
// its own, which a form's reset can't clear, so the <select> keeps its value instead.
const instance = getCurrentInstance();
function bound() {
  const props = instance?.vnode.props;
  return props?.modelValue !== undefined || props?.["model-value"] !== undefined;
}

// The value is only set when it's bound. Setting a <select>'s value to one that no option
// has deselects them all, which would drop the option marked `selected`.
const controlAttrs = () => ({
  ...Object.fromEntries(Object.entries(attrs).filter(([key]) => !onRoot(key))),
  ...(bound() ? { value: model.value } : {}),
});

const select = useTemplateRef<HTMLSelectElement>("select");

function onChange(event: Event) {
  model.value = (event.target as HTMLSelectElement).value;
}

// A ref to the Select gets you the <select>, through `select`.
defineExpose({ select });

onMounted(() => {
  // The options are the caller's, so a server render can't mark the bound one `selected`,
  // and hydrating doesn't set a <select>'s value either, so it's chosen here.
  if (bound() && select.value) select.value.value = model.value ?? "";

  if (import.meta.env.DEV) {
    const el = select.value;
    const named = el?.labels?.length || el?.hasAttribute("aria-label") || el?.hasAttribute("aria-labelledby");
    if (el && !named) {
      console.warn("[Select] has no accessible name: give it a <label for>.", el);
    }
  }
});
</script>

<template>
  <div class="select" v-bind="rootAttrs()" :data-size="size">
    <select ref="select" data-slot="control" :disabled="disabled" v-bind="controlAttrs()" @change="onChange">
      <option v-if="placeholder !== undefined" value="">{{ placeholder }}</option>
      <slot />
    </select>
    <!-- A picture of the select's state, so it's hidden, and presses go through it to the select. -->
    <span data-slot="indicator" aria-hidden="true">
      <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round">
        <path d="m6 9 6 6 6-6" />
      </svg>
    </span>
  </div>
</template>
```

## FAQ

#### Select or something else?

A Select holds one choice out of a list. For other choices, another component will do a better job:

| When people need to…                                              | Use                                                     |
| ----------------------------------------------------------------- | ------------------------------------------------------- |
| Choose one option out of a list, like a country or a time zone    | Select                                                  |
| Choose one option out of a few, which all fit on the screen       | Radio Group, which shows every option without a click   |
| Type to filter a long list, or choose options with icons or more than one line | Combobox                                   |
| Run an action, like Edit or Delete, from a list                   | Dropdown Menu                                           |
| Choose more than one option                                       | A group of Checkboxes, rather than `multiple`           |
| Turn one setting on or off                                        | Checkbox, or Switch                                     |

All of them are on our [Roadmap](/docs/getting-started/roadmap), and they'll share the Select's sizes, states and rules for labels and errors.

::accordion
:::accordion-item{label="Why not rebuild the select with ARIA, so it looks the same everywhere?"}
Because you'd give up more than you'd get. A select-only combobox, as the APG calls it, is a button and a list that you draw and wire up yourself, so you lose the phone's picker, autofill, form submission and reset, typeahead as each system does it, forced colours support and working before JavaScript loads. In exchange, you have to test every key, the focus inside the list, scrolling, positioning near the edges of the screen and the announcements in every screen reader, by hand. Browsers that support `appearance: base-select` now let you style the native picker, which covers most of the reasons people rebuild one (see [The picker](/docs/components/select#the-picker)).
:::

:::accordion-item{label="How do I show a value people can't change?"}
HTML has no read-only state for a `<select>`, and a disabled one leaves its value out of its form. Show the value as text, or in a read-only [Input](/docs/components/input#read-only), which people can still focus and copy. If the form needs to send it, add a hidden input with the same `name` and value.
:::

:::accordion-item{label="Why is there no options prop?"}
Because the options are already HTML. Writing them as `<option>` and `<optgroup>` elements keeps every attribute HTML gives them, renders them on the server without JavaScript and reads the same in every framework. The cost is that your type checker can't tell whether a value matches an option, so keep the options in one typed list and check the value against it, as under [Type-safe](/docs/components/select#type-safe).
:::

:::accordion-item{label="Can I put icons, flags or descriptions in the options?"}
Not in a Select. Only browsers that support `appearance: base-select` draw anything but text in an option, the rest drop it, and screen readers and type-ahead only use the text. If your options need more than words, a Combobox is the better fit.
:::

:::accordion-item{label="Does the Select work before JavaScript loads?"}
Yes. The server renders a real `<select>`, so even before the page hydrates, people can open it, choose an option and send its form. Only the parts that need JavaScript have to wait for it, which are your bound value and your validation.
:::
