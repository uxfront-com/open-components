Next, let's look at how developers use the Dialog. It has one API, with the same names as every other component, it's typed end to end, and it leaves when to open and close it to you.

::framework-switcher
#react
```tsx
import { useState } from "react";
import { Button } from "@/components/Button";
import { Dialog } from "@/components/Dialog";
import { Input } from "@/components/Input";

export function EditProfile() {
  const [open, setOpen] = useState(false);

  function save() {
    // …save the profile, then close the dialog.
    setOpen(false);
  }

  return (
    <>
      <Button onClick={() => setOpen(true)}>Edit profile</Button>
      <Dialog
        id="edit-profile"
        title="Edit profile"
        open={open}
        onClose={() => setOpen(false)}
        actions={
          <>
            <Button variant="outline" onClick={() => setOpen(false)}>Cancel</Button>
            <Button color="primary" onClick={save}>Save changes</Button>
          </>
        }
      >
        <label htmlFor="name">Full name</label>
        <Input id="name" autoComplete="name" />
      </Dialog>
    </>
  );
}
```

```html
<button class="button" type="button" aria-haspopup="dialog" aria-controls="edit-profile" data-variant="solid" data-color="neutral" data-size="md">

</button>

<dialog class="dialog" id="edit-profile" aria-labelledby="edit-profile-title" data-size="md">
  <div data-slot="header">
    <h2 id="edit-profile-title" data-slot="title">Edit profile</h2>
    <button class="button" type="button" data-slot="close" data-variant="ghost" data-color="neutral" data-size="sm" data-icon-only>
      <span data-slot="leading" aria-hidden="true"><svg class="lucide-x">…</svg></span>
      <span data-slot="label">Close</span>
    </button>
  </div>
  <div data-slot="body">
    <label for="name">Full name</label>
    <div class="input" data-size="md">
      <input data-slot="control" type="text" id="name" name="name" autocomplete="name" form="profile" />
    </div>
  </div>
  <div data-slot="actions">
    <form id="profile" method="dialog">
      <button class="button" type="submit" value="cancel" data-variant="outline" data-color="neutral" data-size="md">
        <span data-slot="label">Cancel</span>
      </button>
      <button class="button" type="submit" value="save" data-variant="solid" data-color="primary" data-size="md">
        <span data-slot="label">Save changes</span>
      </button>
    </form>
  </div>
</dialog>

<script type="module">
  const FOCUSABLE =
    'a[href], button:not(:disabled), input:not(:disabled):not([type="hidden"]), select:not(:disabled), textarea:not(:disabled), [tabindex]:not([tabindex="-1"])';
  let opener;

  // A button with aria-haspopup="dialog" opens the dialog it controls, and focus moves
  // to the control marked with data-autofocus, or else the first in its body, then its first action.
  document.addEventListener("click", (event) => {
    const button = event.target.closest('[aria-haspopup="dialog"][aria-controls]');
    const dialog = button && document.getElementById(button.getAttribute("aria-controls"));
    if (!dialog) return;
    opener = button;
    dialog.returnValue = "";
    dialog.showModal();
    const first =
      dialog.querySelector("[data-autofocus], [autofocus]") ??
      dialog.querySelector('[data-slot="body"]')?.querySelector(FOCUSABLE) ??
      dialog.querySelector('[data-slot="actions"]')?.querySelector(FOCUSABLE);
    first?.focus();
  });

  for (const dialog of document.querySelectorAll(".dialog")) {
    // A press on the backdrop lands on the <dialog>, outside its box, and counts when it starts there too.
    const onBackdrop = ({ target, clientX: x, clientY: y }) => {
      const box = dialog.getBoundingClientRect();
      return target === dialog && (x < box.left || x > box.right || y < box.top || y > box.bottom);
    };
    let pressedBackdrop = false;
    dialog.addEventListener("mousedown", (event) => (pressedBackdrop = onBackdrop(event)));
    dialog.addEventListener("click", (event) => {
      if (event.target.closest('[data-slot="close"]')) dialog.close("close-button");
      // An alert dialog needs an answer, so a click outside it doesn't count as one.
      else if (pressedBackdrop && onBackdrop(event) && dialog.role !== "alertdialog") dialog.close("backdrop");
      pressedBackdrop = false;
    });
    // returnValue says why it closed: a button's value, close-button, backdrop, or nothing for Escape.
    dialog.addEventListener("close", () => opener?.focus());
  }
</script>
```
::

Vanilla and Astro have no state to bind `open` to, so their script opens the dialog from the button that controls it, and lets the browser close it. The `close` event's `returnValue` then says why.

## Consistent

Once you've learned the [Button](/docs/components/button/dx#consistent)'s API, you already know most of the Dialog's. These names mean the same thing everywhere in Open Components:

| Name      | Kind  | What it means                                                         |
| --------- | ----- | --------------------------------------------------------------------- |
| `size`    | Prop  | How big the component is, which for a dialog is how wide it gets      |
| `open`    | Prop  | Whether it's showing, for anything that opens on top of the page      |
| `actions` | Slot  | Buttons that act on the component, after everything else              |
| `close`   | Event | People asked to close it, and why                                     |

We recommend `size="md"` and `role="dialog"` as the defaults. The Dialog also leaves a few things out, on purpose:

- There's no `variant` or `color`. A dialog has no intent of its own, so its actions say what it's about, like a Delete project Button with `color="error"`.
- There's no `trigger` slot. The button that opens a dialog is a Button of yours, with its own label and its own place on the page, and the Dialog gives focus back to it on its own.
- There's no `modal` prop. A dialog that leaves the page working, next to what opened it, is a [Popover](/docs/components/popover).
- There's no `closable` prop either. Every dialog closes on `Escape`, and an alert dialog leaves out the close button and ignores the backdrop on its own.

## Type-safe

Props, events and slots are typed, so your editor can autocomplete them and your type checker (`tsc`, `vue-tsc`, `svelte-check`, `ngc` or `astro check`) catches mistakes like `size="xl"`, which isn't one of the Dialog's sizes, or a dialog without a title.

| Prop         | Type                          | Default    | Description                                                                 |
| ------------ | ----------------------------- | ---------- | --------------------------------------------------------------------------- |
| `open`       | `boolean`                     | `false`    | Shows the dialog. It never changes on its own                               |
| `id`         | `string`                      |            | Required. Its title's and description's IDs start with it                   |
| `title`      | `string`                      |            | Required. The heading that names the dialog                                 |
| `description`| `string`                      |            | A sentence or two that screen readers read along with the title             |
| `role`       | `"dialog" \| "alertdialog"`   | `"dialog"` | `alertdialog` for a confirmation that needs an answer                       |
| `size`       | `"sm" \| "md" \| "lg"`        | `"md"`     | How wide it gets, at most                                                   |
| `closeLabel` | `string`                      | `"Close"`  | The close button's label, for other languages                               |

| Event   | Payload                                                         | Description                                                    |
| ------- | --------------------------------------------------------------- | -------------------------------------------------------------- |
| `close` | `"escape" \| "close-button" \| "backdrop" \| "action" \| "closed"`, `string` | Fires when people ask to close it, with why, and for `action`, the value of the button that sent the `<form method="dialog">`. Fires with `closed` when it's already closed |

Angular is the one framework where two of these names change, since its Dialog sits on the `<dialog>` itself. A `title` attribute stays on the element even when an input reads it, which would show the title as a tooltip over the whole panel, so the title is `dialogTitle`. `close` is already the `<dialog>`'s own event, and an output carries a single value, so the event is `closeRequest`, with `{ reason, value }`.

| Slot      | Description                                                                         |
| --------- | ----------------------------------------------------------------------------------- |
| `default` | The content, like a message or a form, which scrolls when it doesn't fit            |
| `actions` | The Buttons that answer the dialog, like Cancel and Save, in the order people read them |

## Composable

The Dialog renders the `<dialog>` as its root, so everything you pass lands on it, including classes, styles, data attributes and event listeners. Its title and description get their IDs from the dialog's own `id`, as in `edit-profile-title`, so you can point at them from elsewhere, like a test.

### Forms

A `<form method="dialog">` is how HTML answers a dialog. On its own, it closes the dialog and sets `returnValue` to the value of the button that sent it. The Dialog asks instead, firing `close` with the reason `action` and that value, so you decide what happens, the same way as for every other reason. That also means the answer works before your JavaScript loads, in Astro and Vanilla.

::framework-switcher
#react
```tsx
<Dialog
  id="delete-project"
  role="alertdialog"
  title="Delete project?"
  open={open}
  onClose={(reason, value) => {
    setOpen(false);
    if (value === "delete") deleteProject();
  }}
  actions={
    <form method="dialog">
      <Button type="submit" value="keep" variant="outline">Keep project</Button>
      <Button type="submit" value="delete" color="error">Delete project</Button>
    </form>
  }
/>
```

A form in the body works like any other, so a dialog that edits something can send it with a submit Button among its actions, through the button's `form` attribute, and close once it's saved.

### With other components

- A [Button](/docs/components/button) opens the dialog, and gets focus back when it closes. The close button is a Button too, and so are the actions, with their names, focus rings and `type="button"`.
- An [Input](/docs/components/input) in the body gets the focus when the dialog opens, if it's the first control there, and keeps its label and error message as it would anywhere else.
- A [Spinner](/docs/components/spinner) shows that an action is under way, inside its Button, with `loading`, which keeps the focus on the Button while the dialog waits.
- A [Popover](/docs/components/popover) or a [Tooltip](/docs/components/tooltip) inside a dialog opens in the top layer too, above the dialog, and closes on `Escape` before it does, and so will the menus on our [Roadmap](/docs/getting-started/roadmap).

## Controllable

The Dialog doesn't keep any state you can't reach. Whether it's open is yours, and so is everything that happens when people ask to close it:

| State          | How you control it                                                                          |
| -------------- | ------------------------------------------------------------------------------------------- |
| Open           | `open`, which it never changes on its own                                                   |
| Closing        | `close`, with why, after which you set `open` to false, or keep it open, unless it's `closed` |
| Initial focus  | `data-autofocus` on the control to start on                                                 |
| Focus after    | Back to the opener on its own, or anywhere you move it once `open` is false                 |
| Role           | `role`, which also decides the close button and the backdrop                                |

## DX Checklist

| Rule                       | Level  | Scope     | Requirement | Basis | Check |
| -------------------------- | ------ | --------- | ----------- | ----- | ----- |
| `dialog/shared-vocabulary` | Must   | Component | It uses the shared names: `open`, `size`, `actions` and `close` (`closeRequest` in Angular) | Open Components | Review |
| `dialog/typed`             | Must   | Component | Props, events and slots are typed, with unions rather than `string`, and `id` and `title` (`dialogTitle` in Angular) are required | Open Components | Type check |
| `dialog/controllable`      | Must   | Component | It opens and closes with `open`, and asks rather than closing itself: `Escape`, the close button and the backdrop fire `close`, with why, and when a browser closes it anyway, it fires `close` with `closed` | Open Components | Unit test |
| `dialog/root-attributes`   | Must   | Component | Attributes, classes and listeners land on the `<dialog>` | Open Components | Unit test |
| `dialog/form-actions`      | Should | Component | A `<form method="dialog">` inside it fires `close` with the reason `action` and its button's value, rather than closing it | HTML | Unit test |

## FAQ

::accordion
:::accordion-item{label="Why does the Dialog ask, rather than close itself?"}
So you can keep it open when people would lose something, like what they've typed. Every way of closing it fires `close`, with why, and you set `open` to false, which most of the time is all your handler does. The one close you can't turn down is the browser's own, after a close request it won't let the page refuse, and `close` then fires with `closed`, so set `open` to false for it, and the dialog and your code stay in step.
:::

:::accordion-item{label="What about the closedby attribute?"}
`closedby="any"` asks the browser to close a dialog on a press outside it, on top of `Escape`, which is what our backdrop handling does. It closes the dialog itself, though, rather than asking you first, so the Dialog handles the backdrop on its own, the same way it handles every other reason.
:::

:::accordion-item{label="Does the Dialog work before JavaScript loads?"}
Partly. Opening a modal dialog takes `showModal()`, so a dialog can't open before your JavaScript loads. Everything inside it is plain HTML, though, so once it's open, a `<form method="dialog">` answers it, and the browser closes it on `Escape`, even in Astro and Vanilla, where no framework is running.
:::
::
