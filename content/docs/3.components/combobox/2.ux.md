Now let's look at how a combobox behaves: how assistive technologies read it, what each key does, how it filters, what happens to text that isn't an option, and how it works in a form and on a phone.

## Accessible

### Use a text field with the combobox role

A combobox is an `<input>` with `role="combobox"`, and a `listbox` of options that it controls. We follow the APG's [Editable Combobox With List Autocomplete](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/examples/combobox-autocomplete-list/), the kind the [combobox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/) calls list autocomplete with manual selection, where "the character string the user has typed will become the value of the combobox unless the user selects a value in the popup". The text field carries the attributes that make it one:

- `aria-autocomplete="list"` tells screen readers that typing narrows a list of suggestions, rather than completing the text in place ([WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/#aria-autocomplete)).
- `aria-expanded` says whether the panel is open, and `aria-controls` points at it, so a screen reader can say there's a list and how to reach it.
- `aria-activedescendant` points at the highlighted option while the panel is open, which is how screen readers read the option without focus leaving the text.

The pattern lists three other kinds, and we turned them all down. With no autocomplete, the list shows the same options whatever people type, which doesn't help them find one in a long list. With automatic selection, "the first suggestion is automatically highlighted as selected", so `Enter` and blur pick it, and people who type "Fra" for a place called Fra get France. With inline autocomplete, the rest of the first match is typed into the field as selected text, which gets in the way of people typing with an input method, like Japanese, and of screen readers that read the selection out on every key.

### Name every combobox

Give every combobox a visible label, from a [Field](/docs/components/field) or a `<label for>`, since the text field is an `<input>` and the label names it the same way it names an Input ([WCAG 3.3.2](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)). The panel takes the same name, so people hear "Country, listbox" when they reach it. The toggle has a name of its own, "Suggestions" by default, which voice control users can say, while its `aria-expanded` says whether the list is showing.

### Keep focus in the text

Focus stays in the text field the whole time, while the arrow keys move a highlight through the options. That way people can keep typing to narrow the list, whatever's highlighted, and screen readers hear each highlighted option through `aria-activedescendant`. A press on an option doesn't take focus either, and neither does a press on the toggle, which is out of the tab order, as in the APG's example.

The highlight is a 2px outline in the focus colour, the same as the field's focus ring, so people who use the keyboard can see where they are in the list.

### Contrast and size

The text, the placeholder and "No results" have at least 4.5:1 against the page, and the border, the chevron and the focus ring at least 3:1 ([WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)). The toggle and each tag's remove button are at least 24 × 24px to press ([WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)), and on touch screens they and the options reach 44px tall, which is what [WCAG 2.5.5](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html) asks for at level AAA.

## Predictable

### Keyboard

Every key works without a pointer ([WCAG 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)). Letters, `Space`, `Home`, `End`, `ArrowLeft` and `ArrowRight` edit the text, as they do in any text field, and the rest work the list:

| Key              | With the panel closed                                                   | With the panel open                                                                  |
| ---------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| A letter         | Types it, filters the list and opens it                                 | Types it and filters the list, with nothing highlighted                              |
| `ArrowDown`      | Opens it on the first option                                            | Moves the highlight down, skipping disabled options, and stops at the last           |
| `Alt+ArrowDown`  | Opens it with nothing highlighted                                       | The same as `ArrowDown`                                                              |
| `ArrowUp`        | Opens it on the last option                                             | Moves the highlight up, and stops at the first                                       |
| `Alt+ArrowUp`    | Nothing                                                                 | Closes it, and keeps the text                                                        |
| `PageDown`, `PageUp` | Nothing                                                             | Moves the highlight ten options, as on the Select                                    |
| `Enter`          | Settles the text, then submits the form                                 | Picks the highlighted option and closes it, or with `multiple`, toggles it and stays open. With nothing highlighted, settles the text |
| `Tab`            | Settles the text and moves on                                           | Picks the highlighted option, closes it and moves on. With `multiple`, settles the text |
| `Escape`         | Clears the text, and the value too for a single value                  | Closes it, and keeps the text                                                        |
| `Backspace`      | Deletes text. With `multiple` and no text, removes the last value       | Deletes text                                                                          |

Both presses of `Escape` stop there, so a Dialog around the Combobox stays open, and only once there's nothing left to clear does `Escape` reach it. That's the APG's example, where `Escape` "closes" the list if it's showing, and "clears the textbox" if it isn't. "Settles the text" is what [Decide what happens to text that isn't an option](/docs/components/combobox/ux#decide-what-happens-to-text-that-isnt-an-option) describes.

Here's where it differs from the [Select](/docs/components/select/ux#keyboard), whose control is a button, so its keys don't have text to edit:

| Key                | Select                                   | Combobox                                    |
| ------------------ | ---------------------------------------- | ------------------------------------------- |
| A letter           | Jumps to the option that starts with it  | Types it, and filters the list              |
| `Space`            | Opens the panel, or picks                | Types a space                               |
| `Home`, `End`      | Move to the first or last option         | Move the caret                              |
| `Enter`, closed    | Opens the panel                          | Settles the text and submits the form       |
| `Escape`, closed   | Goes on to the page                      | Clears the text                             |
| `Backspace`        | Removes the last value, with `multiple`  | Deletes text, then removes the last value   |

### Open it when people ask for it

The panel opens when people type, press `ArrowDown` or `ArrowUp`, or press the toggle, and not when the text field gets focus. People tab through a form to reach the field after it, and a list that opens on every stop covers the fields below it, which is why React Aria's [ComboBox](https://react-aria.adobe.com/ComboBox) opens on input by default too.

It closes when people pick an option, unless they're picking several, press `Escape`, leave the field or press anywhere outside it. A press in the text, while the panel is open, only moves the caret, so people can fix a typo without losing the list.

### Filter as people type

We recommend matching any part of an option's label, ignoring case and accents, so "zealand" finds New Zealand and "cote" finds Côte d'Ivoire. People often remember a word from the middle of a name, and plenty of names start with words like "Republic of" or "Saint", so matching only the start would hide what they're after. Accents are the same: people type on keyboards that don't have them, and a list that wants "Zü" to find Zürich fails them. [React Aria's `useFilter`](https://react-aria.adobe.com/useFilter) does the same with its `contains` and `sensitivity: "base"`.

| Matching     | "zea" finds New Zealand | "fra" finds France | When it's best                                             |
| ------------ | ----------------------- | ------------------ | ---------------------------------------------------------- |
| Any part     | Yes                     | Yes                | Names people might remember a word of, which is most lists |
| The start    | No                      | Yes                | Codes and lists people type from the start, like airports  |

Groups with no match hide along with their headings, and separators with nothing on one side of them do too. When your list needs to match another way, like on a code as well as a label, give it a `filter` of your own.

### Don't pick an option for people

Typing never highlights an option, so `Enter` and blur never pick one people didn't choose. They press `ArrowDown` to move into the list, or press an option, and only then does it become the value. That's what keeps "Fra" from turning into France on its way to the form, and what makes text that isn't an option possible at all.

### Say when nothing matches

When nothing matches, the panel stays open and says "No results", so people know the list is empty rather than broken. It isn't an option, so it doesn't take the highlight, and since a listbox may only hold options and groups, it's hidden from assistive technologies, which hear it as a status message instead ([WCAG 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)). With `creatable`, the create option takes its place.

### Announce the count once typing pauses

As people type, a screen reader can't see the list grow or shrink, so the Combobox announces how many options match, like "3 results". It waits until typing pauses for 1400ms, the same as GOV.UK's [accessible-autocomplete](https://github.com/alphagov/accessible-autocomplete), since a count on every key would talk over the letters people hear as they type. With no match, it announces "No results", or the create option's label.

### Decide what happens to text that isn't an option

People type, then leave. When they press `Tab`, press `Enter` on a closed panel or move focus away, the Combobox settles the text:

- Text that's an option's label, ignoring case and accents, picks that option, so "zurich" becomes Zürich.
- Empty text clears the value.
- Any other text goes back to the picked option's label, or to empty, and the value doesn't change.

That last case is the one to watch. A text field that keeps "Fra" on screen, while the form submits France, or nothing, tells people one thing and sends another. So unless you turn on one of the props below, text that isn't an option doesn't stay.

`Escape` works the other way. Its first press closes the panel and leaves the text as it is, so people can keep editing, and its second clears the text, and the value too for a single value, the way the APG's example does.

### Keep text people type, when you allow it

Some fields take values that aren't in the list, like a city you don't ship to yet, or a new tag. Two props allow it, and both are off by default, since a value nobody can pick again is often a typo:

- `allowCustomValue` keeps the text as it was typed, as the value, when people leave the field. It's for one value, the way [Ark UI](https://ark-ui.com/docs/components/combobox) names it, and like [React Aria's](https://react-aria.adobe.com/ComboBox) `allowsCustomValue` and [Material UI's](https://mui.com/material-ui/react-autocomplete/) `freeSolo`.
- `creatable` ends the list with an option like 'Create "Lyon"', which people pick like any other. It fires `create` with the text, so your code can add it to the list, the pattern Material UI calls "Creatable".

Here's what the form gets under the Combobox's `name` in each case:

| What people did                       | One value                           | With `multiple`                       |
| ------------------------------------- | ----------------------------------- | ------------------------------------- |
| Picked an option                      | Its `value`, like `fr`, not its label | Each one's `value`                  |
| Typed text, with `allowCustomValue`   | The text, without spaces at its ends | Nothing: it's ignored                |
| Picked the create option              | The text                            | The text, along with the others       |
| Typed text, with `creatable`, without picking the create option | The value it had before | The values it had before |
| Typed text, with both props           | The text, kept on blur, or created from the create option | Nothing new, unless it's created |
| Typed text, with neither prop         | The value it had before             | The values it had before              |
| Picked nothing                        | Nothing                             | Nothing                               |

Text that's the same as an option's `value`, but not its label, like "es" for Spain, would submit as that option, so neither prop keeps it or offers to create it: it goes back like any other text. So give your options values people won't type as a new one, like IDs or codes.

With `multiple`, `allowCustomValue` does nothing, and the reference implementation warns you during development. Turning whatever people type into a value, one after another, is what a Tags Input does, so new values come only from the create option there.

### Several values, or a Tags Input

With `multiple`, a Combobox picks several options, each a tag, the way the Select's `multiple` does. React Aria, Ark UI, [Base UI](https://base-ui.com/react/components/combobox) and Material UI all put several values on the combobox too. It's still a list people pick from, so the values are options, and new ones come one at a time through `creatable`.

A Tags Input is another component, where people type any text and a comma, `Enter` or a paste splits it into tags they can edit, like email addresses or keywords. [Mantine](https://mantine.dev/core/tags-input/) and [Ark UI](https://ark-ui.com/docs/components/tags-input) make it a component of its own, even where it's built on their combobox, and so do we, since its keys, its value and its validation all work another way.

### Remove a value by pointer and by keyboard

With `multiple`, each tag has a real `<button>` to remove it, named after its value, like "Remove France", so voice control users can say it and screen readers read it. Once a value is removed, focus goes to the next tag's button, or back to the text when there's none, so keyboard users never fall back to the top of the page, and screen readers hear "France removed" ([WCAG 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)). `Backspace` in empty text removes the last value too, as people expect from a field of tags.

### Let the form do its work

A hidden native `<select>` is always in the page, so the Combobox takes part in its form the way a Select does: it submits under its `name`, blocks a submit while it's `required` and empty, and goes back to its first value when the form resets, with that value's text. The `<select>` holds an option for each value people typed, so those submit and reset too. The text field has no `name`, since what people are typing isn't the value until it's picked or kept.

## Every state

### Closed

The field shows the picked option's label, or the placeholder, or with `multiple`, the tags under empty text. The chevron points down.

### Open

The panel shows every option when it opens on a picked value, so people see what else they could pick, and only the matches once they type. The highlight shows where the arrow keys are, and a check mark shows what's picked.

### Disabled

A disabled Combobox is dimmed, can't take focus or open, and leaves its form, like any disabled control. Try to explain why it's disabled near it, since people can't reach it to find out.

### Read-only

A read-only Combobox keeps its value, its contrast and its place in the tab order, and submits with its form, but doesn't open, and its tags lose their remove buttons.

### Invalid

While its Field has an error, the text field has `aria-invalid="true"` and is described by the message, so screen readers read the error with the field, and its border takes the error colour.

### Long and empty

Long labels wrap in the panel, rather than widening it past the field, and in a tag they're cut short with an ellipsis. An empty list says "No results", and a list that's still empty before people type is one to fill in, since a combobox with nothing to suggest is a text field.

## Adaptive

### Make room for the on-screen keyboard

On a phone, the on-screen keyboard comes up as soon as the text field has focus, and covers a large part of the screen. It shrinks the visual viewport, but not the layout viewport, and CSS anchor positioning works against the layout one, so a panel placed below the field can open behind the keyboard. So while the keyboard is up, the Combobox places the panel itself, in the part of the screen the keyboard leaves, from the [Visual Viewport API](https://developer.mozilla.org/en-US/docs/Web/API/Visual_Viewport_API), above the field when there's more room there, and it goes back to anchor positioning once the keyboard closes.

There's no native picker to fall back to, as the Select has. A `<select>` can't take typed text, and the text field that brings up the keyboard is the whole point. We test the scripted placement with a stand-in for the visual viewport, and the rest in a browser's emulation, which has no keyboard, so check it on a real phone too.

### Let autofill help where it should

The text field has `autocomplete="off"` by default, since a browser's own list of past entries opens over the panel and hides the options. Where the Combobox asks people about themselves, like the country they live in, give it the field's name instead, like `autocomplete="country-name"`, so browsers and assistive technologies can fill it in ([WCAG 1.3.5](https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html)). When autofill types an option's label, the Combobox picks that option.

The text field also has `spellcheck="false"` and `autocapitalize="off"`, since names in a list, like Curaçao, aren't dictionary words to underline, and a phone that capitalises the first letter would get in the way of people searching for a word in the middle of a name.

### Zoom, forced colours and motion

The field and the panel fit a 320px-wide screen at 400% zoom without scrolling sideways ([WCAG 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)), since the panel is never wider than the screen and long labels wrap. In forced colours, focus, the highlight and the panel's edge take system colours. When people ask for less motion, the chevron and the panel don't animate.

## FAQ

### Combobox or Select?

We recommend the [Select](/docs/components/select) when the list is short enough to scan, since it's one press to open and one to pick, and phones show their own picker for it. Reach for the Combobox when the list is long enough that people would rather type than scroll, like countries or people, or when they need to add a value that isn't in it.

| When you need to…                                         | Use                                               |
| --------------------------------------------------------- | ------------------------------------------------- |
| Pick one option out of a few, which fit on the screen     | [Radio Group](/docs/components/radio-group)       |
| Pick one option, or several, out of a list people scan    | [Select](/docs/components/select)                 |
| Type to filter a long list, and pick one or several       | Combobox                                          |
| Keep a value that isn't in the list                       | Combobox, with `allowCustomValue` or `creatable`  |
| Type any number of free values, like email addresses      | Tags Input                                        |

::accordion
:::accordion-item{label="Why doesn't Enter pick the first match?"}
Because people didn't choose it. With "Fra" typed, the first match might be France, while the person meant Fra, or was about to type more. Picking it anyway changes what they typed on their way to the form, and it's the kind of mistake people only notice after they've submitted. So `Enter` picks only what's highlighted, and `ArrowDown` is one press away.
:::

:::accordion-item{label="Why is the empty message hidden from screen readers?"}
Because a listbox may only hold options and groups, and a screen reader that finds text inside one reads it as an option people could pick. So the message is drawn for people who see it, and announced as a status message for people who don't, which is how screen reader users hear it anyway, since their focus stays in the text.
:::
::
