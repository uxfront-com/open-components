Radio groups let people pick one option out of a few, like a delivery speed or a plan, while every option stays in view. They look like a list of circles with words beside them, which is why they're so often built from scratch. Think of radios that each have their own `name`, so people can check all of them at once, a question that's a heading rather than a legend, so screen readers never read it, or a group that turns red when people skip it, but doesn't tell screen reader users anything at all.

This page walks you through building one the right way. We'll look at:
- **User Interface** (UI) - how a radio group looks
- **User Experience** (UX) - how it behaves for every person and every input
- **Developer Experience** (DX) - how developers work with it
- **Agentic Experience** (AX) - how agents can read and verify it

Every example on this page runs on our [reference implementation](/docs/components/radio-group#reference-implementation), which does its part of every rule in the [checklist](/docs/components/radio-group#checklist), so feel free to click and arrow through them as you read. The code under each example comes in React, Vue, Svelte, Angular, Solid, Astro and Vanilla, written for a Radio Group with the same API in each. Pick yours from the Framework select above the sidebar. Vanilla is plain HTML and JavaScript, so it writes out the markup from the [DOM contract](/docs/components/radio-group#deterministic).

The Radio Group is the question, and each Radio inside it is one answer. The group renders its legend, its hint and its error message, since a fieldset needs its legend inside it, and its radios share its name, its size and its value, so they can never disagree.

## User Interface (UI)

Let's start with how a radio group looks: its parts, its sizes, how it shows each of its states and how to lay out its options.

### Anatomy

::radio-group-anatomy
1. **Group** — The `<fieldset>`, which groups the radios and carries the size.
2. **Legend** — The question the radios answer, which names the group.
3. **Hint** — Optional. Help that applies to every option, which describes the group.
4. **Radio** — One option, its indicator and its label, which people can press anywhere.
5. **Indicator** — The native radio, drawn as a ring, which fills with a dot once it's checked.
6. **Label** — The option's text, which names its radio.
::

Every radio group has a group, a legend and two or more radios. An error message, when there is one, sits between the hint and the radios, so people read what's wrong before they choose again. The parts always render in the same order, which you can see in the [DOM contract](/docs/components/radio-group#deterministic).

| Size | Row min. height | Text | Indicator | Gap |
| ---- | --------------- | ---- | --------- | --- |
| `xs` | 24px            | 12px | 14px      | 4px |
| `sm` | 32px            | 14px | 16px      | 8px |
| `md` | 36px            | 14px | 16px      | 8px |
| `lg` | 40px            | 16px | 20px      | 8px |
| `xl` | 48px            | 16px | 20px      | 8px |

Sizes are set in `rem`, and the table shows the values we recommend at the default text size of 16px. Each row is as tall as an [Input](/docs/components/input#sizes) of the same size, and its text is the same size too, so a radio lines up with an input beside it, as under [Layout](/docs/components/radio-group#layout). The indicator on its own is only 14 to 20px, which is why the label is part of the target: pressing it checks the radio, so every radio is at least 24 × 24px with its label ([WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). On touch screens, each row grows to at least 44px tall. The heights are minimums, so a row grows with larger text, or with a label that wraps.

Each state has a look of its own, styled from the attribute that exposes it, on the `<input>` or on the group. That way, what people see and what assistive technologies report can never drift apart, and a group can't look invalid without actually being invalid.

| State    | Selector                                               | Recommended look                                                |
| -------- | ------------------------------------------------------ | --------------------------------------------------------------- |
| Hover    | `:hover`, inside `@media (hover: hover)`               | The ring at 80% of the text colour, up from 55%                 |
| Focus    | `input:focus-visible`                                  | A 2px outline, 2px from the ring, in `--color--focus`           |
| Checked  | `:has(> input:checked)`                                | The ring filled with `--color--primary`, and a dot inside it    |
| Disabled | `:has(> input:disabled)`                               | 50% opacity and a `not-allowed` cursor                          |
| Invalid  | The group's `[aria-invalid="true"]`                    | A 2px ring in `--color--error-text`, and the error message      |

A checked radio is filled as well as dotted, so it differs from the others by its shape, and not by its colour alone ([WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)). A radio inside a disabled group matches `:disabled` too, since a disabled `<fieldset>` disables every form control inside it, so one selector covers both. We recommend leaving `:invalid` out of it, for the same reason as on the [Input](/docs/components/input#states): it matches a required group before anyone has had a chance to answer it.

None of the states change a radio's size or position. The invalid ring's second pixel is drawn inside the indicator, and the focus ring outside it. You'll find how each state behaves under [Every state](/docs/components/radio-group#every-state).

### Layout

The Radio Group stacks its radios, one per line, each as wide as its label. That's why it doesn't have a prop for its direction. We recommend keeping them stacked, since people scan a column faster than a row, the order they read the options in is the order the arrow keys take, and a long label can wrap without pushing the next option onto a line of its own.

An option sometimes needs more than its label, like "Other", which needs an input to say what it is. Put the [Input](/docs/components/input) beside its radio, inside the group, with the same size, and the two line up:

::framework-switcher

`.other` is a flex row of yours, like `display: flex; align-items: center; gap: 0.75rem`, with the Input set to fill what's left. Here's what to keep in mind:

- Typing in the input checks "Other", so people don't have to do both. Checking it when the input only gets focus would change the answer of anyone who tabs past it.
- The input's name includes the option's, "Other, how you heard about us", so screen readers don't announce an input called "Other" with no question.
- Keep the input in the page whether "Other" is checked or not, so it stays in the same place in the tab order, which is right after the group.

### Tokens

The radio group reads five [theme tokens](/docs/foundations/design-tokens#theme-tokens), which every component shares:

| Token                       | Used for                                                                       |
| --------------------------- | ------------------------------------------------------------------------------ |
| `--color--neutral-text`     | The legend and labels, and mixed into the rings and the hint                   |
| `--color--primary`          | The fill of a checked radio                                                    |
| `--color--primary-contrast` | The dot on top of it                                                           |
| `--color--error-text`       | The rings and the error message of an invalid group                            |
| `--color--focus`            | The focus ring, which is the same for every component                          |

The ring is the text colour at 55%, which needs 3:1 against the page, since an empty radio is nothing but its ring, and 80% on hover. The hint is the text colour at 70%, which needs 4.5:1. With our reference tokens, from the Tailwind CSS palette, the ring comes to 3.5:1 and the hint to 5.6:1 on white, and 5.0:1 and 7.4:1 on zinc-900, as with the Input.

The checked fill comes to 6.4:1 against white and 5.7:1 against zinc-900, and the dot to 6.4:1 against the fill in both. If you change the tokens, make sure to check the same pairs. You'll find the tokens themselves in the Button's [`tokens.css`](/docs/components/button#reference-implementation), which you can copy into your theme.

If you need to tune a radio group, you can set its [own variables](/docs/foundations/design-tokens#component-variables), such as `--radio-group--gap`, from a class on the group, and each Radio's, such as `--radio--indicator--size`, from a class on the Radio. Their styles sit in the `components` cascade layer, so your class wins without any specificity tricks:

::framework-switcher

## User Experience (UX)

Now let's look at how a radio group behaves for every person, input and setting. A good radio group is [accessible](/docs/components/radio-group#accessible), [predictable](/docs/components/radio-group#predictable), designed in [every state](/docs/components/radio-group#every-state) and [adaptive](/docs/components/radio-group#adaptive).

### Accessible

#### Use native radios

A native `<input type="radio">` gives you the `radio` role, its checked state, a single `Tab` stop for the whole group, the arrow keys, a label you can press, form submission and `required`, all for free. An element with `role="radio"` only gives you the role. You'd have to rebuild the rest by hand, from moving `tabindex` around as people press the arrow keys to a hidden input that sends the value, and every one of those is one more thing to get wrong.

- Every group has a `<fieldset>` and a `<legend>` that asks the question its radios answer ([WCAG 1.3.1](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html), [3.3.2](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)). A heading or a paragraph above the radios looks the same, but screen readers don't read it when focus enters the group, so people hear "Express, radio button" with no question at all.
- Keep the legend short, since some screen readers read it again with every radio. Anything longer goes in the hint.
- A hint that applies to every option goes in the group's description, which screen readers read after its name. The Radio Group links it with `aria-describedby` for you, from its `hint`.
- Every radio has a visible label. The label wraps its input, so it names the radio without an `id`, and pressing anywhere on it checks the radio, which makes for a much bigger target than the indicator.
- Every radio in a group shares the group's `name`, and every group on the page has a name of its own. Browsers make a group out of the radios that share a name in the same form, so two groups with one name become one, and radios with different names let people check more than one.

#### Contrast and size

- The legend, the labels, the hint and the error message need a contrast of at least 4.5:1 with their background, since people need to read them ([WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)). Disabled radios are exempt, but they should still be readable.
- The ring of an unchecked radio, and the fill of a checked one, need 3:1 against the page ([WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)). An unchecked radio is nothing but its ring, so it's how people see that the option is there at all. The focus ring needs 3:1 as well.
- Every radio is at least 24 × 24px with its label ([WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). On touch screens, each row grows to 44px tall ([WCAG 2.5.5](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)).

#### Show focus

When a radio has focus, its indicator shows an outline in the same focus colour as every other component ([WCAG 2.4.7](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)). Like the Button's, it's at least 2px thick and drawn outside the ring, and we recommend 2px for both. Browsers only match `:focus-visible` on a radio when people use the keyboard, so a click checks the radio without a ring, while an arrow key shows people where they are.

You'll also want to keep focused radios clear of sticky headers and footers, which you can do with `scroll-padding` ([WCAG 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html), [2.4.12](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-enhanced.html)).

### Predictable

#### Keyboard

| Key                         | Radio Group                                                                                     |
| --------------------------- | ----------------------------------------------------------------------------------------------- |
| `Tab`                       | Moves focus into the group, onto the checked radio, or the first one when none is checked, and on out of it |
| `Shift+Tab`                 | Moves focus back into the group, onto the checked radio, or in Chrome the last one when none is checked, and back out of it |
| `ArrowDown`, `ArrowRight`   | Moves focus to the next radio and checks it, skipping disabled ones, from the last back to the first |
| `ArrowUp`, `ArrowLeft`      | Moves focus to the previous radio and checks it, from the first back to the last                |
| `Space`                     | Checks the radio with focus, when none is checked yet                                           |

That's all the browser's doing, from the radios' shared `name`, and it's the keyboard the APG's [Radio Group](https://www.w3.org/WAI/ARIA/apg/patterns/radio/) pattern asks for ([WCAG 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)), apart from one case. With nothing checked, the APG puts focus on the first radio however people tab in, while Chrome puts it on the last one with `Shift+Tab`, which the APG notes some browsers do. Since it's the browser's choice, we leave it be. A group is one stop in the tab order, so people can tab past a long list of options in one go, and the arrow keys check as they move, so there's always one answer once people have started.

#### Don't act on change

Checking a radio never submits its form, opens another page or moves focus ([WCAG 3.2.2](https://www.w3.org/WAI/WCAG22/Understanding/on-input.html)). Keyboard users check every option between the one they're on and the one they want, so a group that acts on each one sends them somewhere they never meant to go. Wait for the form's submit button, and if an answer brings up a follow-up question, put it right after the group, where people will reach it next.

#### Choose a default with care

Once people have checked a radio, they can't go back to having none checked, so a default is an answer they never gave unless they notice it. We recommend checking one by default only when it's safe and most people would pick it anyway, like "Standard" delivery. Otherwise, leave all of them unchecked and make the group `required`, so people read the question and answer it. If "none of these" is a real answer, give it a radio of its own.

#### Write options people can tell apart

- Keep labels short, and start each one with the words that set it apart, as in "Express, the next working day".
- Make sure the options don't overlap and cover every answer, adding one like "Other" or "I'm not sure" when they don't.
- Put them in an order people can predict, like cheapest first, or the most common first.
- Keep it to a few options that fit on the screen. When there are many, like countries, a Select fits better (see [FAQ](/docs/components/radio-group#faq)).

### Every state

#### Checked

One radio in a group is checked at a time, and checking another unchecks it. Its form sends the checked radio's `value` under the group's `name`, and nothing at all while none is checked. A checked radio is filled and dotted, so it's clear at a glance, in colour or not.

#### Disabled

You can disable one radio, or the whole group. A disabled radio can't be focused or checked, the arrow keys skip it, screen readers announce it as dimmed or unavailable, and its form leaves it out. A disabled group sets `disabled` on its `<fieldset>`, which disables every radio inside it in one go, so its value is left out of the form too.

We recommend disabling as little as you can. A disabled option can't explain why it's unavailable, so say why in its label, as in "Next day (not available for this address)", or leave it out. Never disable a radio while it has focus, either, since the browser takes the focus away, and keyboard and screen reader users lose their place.

#### Invalid

An invalid group needs an answer, or a different one, and an error message that says what to do. The Radio Group shows the state while its `error` is set, and the page decides when to set it, since only the page knows what makes an answer right.

Its look has to match what screen readers announce, and ARIA only supports `aria-invalid` on some roles. `radiogroup` is one of them, while `group`, the role a `<fieldset>` has, and `radio` aren't ([WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/#aria-invalid)). So the Radio Group gives its `<fieldset>` the `radiogroup` role, and sets `aria-invalid="true"` on it while its error shows. The fieldset still takes its name from its `<legend>`, since the [HTML Accessibility API Mappings](https://www.w3.org/TR/html-aam-1.0/#fieldset-element-accessible-name-computation) name a fieldset from its legend whatever its role. The red rings read the same attribute, so they show exactly when screen readers say the group is invalid.

```tsx
import { useRef, useState, type FormEvent } from "react";
import { flushSync } from "react-dom";

export function Checkout() {
  const [delivery, setDelivery] = useState("");
  const [error, setError] = useState("");
  const [status, setStatus] = useState("");
  const first = useRef<HTMLInputElement>(null);

  function answer(value: string) {
    setDelivery(value);
    // An answer fixes the error, so it clears as soon as there is one.
    setError("");
  }

  async function order(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    if (!delivery) {
      // Focus once the error is in the page, so screen readers read it with the group.
      flushSync(() => {
        setError("Choose how you'd like your order delivered");
        setStatus("Couldn't place your order. Check the delivery options.");
      });
      first.current?.focus();
      return;
    }
    await api.order(delivery);
    setStatus("Order placed");
  }

  return (
    <form noValidate onSubmit={order}>
      <RadioGroup
        name="delivery"
        legend="How would you like it delivered?"
        required
        error={error}
        value={delivery}
        onChange={(event) => answer(event.target.value)}
      >
        <Radio ref={first} value="standard">Standard</Radio>
        <Radio value="express">Express</Radio>
      </RadioGroup>
      <Button type="submit" color="primary">Place order</Button>
      <p role="status">{status}</p>
    </form>
  );
}
```

```html
    status.textContent = "Order placed";
  });
</script>
```
::
::

- Say what to do, as in "Choose how you'd like your order delivered", rather than "This field is required" ([WCAG 3.3.3](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html)). The Radio Group puts the message above the radios and links it to the group with `aria-describedby`, so screen readers announce the group as invalid and read the message after its legend ([WCAG 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)). The red rings alone can't say any of that, and they mean nothing to people who can't tell red apart ([WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)).
- Check a group when people submit, and not when they pass through it. Someone who tabs past a question hasn't answered it yet, and may well come back. Once an error shows, clear it as soon as they check a radio, since any answer fixes a missing one.
- When a submit fails, move focus to the first radio of the first invalid group, so screen readers read its legend, its error and the radio together. Do it once the error is in the page, which in most frameworks means waiting for the next render, as above. With several errors, a summary at the top of the form, with a link to each group, works even better.
- Put `novalidate` on the form, so that the browser's own error bubbles don't compete with yours, and keep `required` on the group, which tells screen readers that it's required.

### Adaptive

#### Pointer, touch and pen

- Hover styles only apply to pointers that can actually hover (`@media (hover: hover)`), otherwise a tap would leave the ring looking hovered.
- On touch screens, each row is at least 44px tall, so a finger lands on the option it meant to, without the radios looking any bigger.
- The whole label checks its radio, but each row is only as wide as its label, so pressing the empty space beside an option doesn't check it by surprise.

#### More contrast

When someone asks for more contrast (`prefers-contrast: more`), as with Increase contrast on macOS and iOS, the rings are drawn in the text colour at full strength, rather than at 55%. The labels and the hint already pass 4.5:1, so they stay as they are.

#### Forced colours

Windows contrast themes replace every colour with the user's own, and drop backgrounds and shadows, which is what draws the dot. So in these themes, the Radio Group lets the browser draw its own radios, which follow the user's colours, checked state and all. Focus is drawn with `outline`, and a disabled radio's label is marked with `GrayText`. The invalid ring is a colour and a shadow, which forced colours replace, so it's the error message, in text, that tells people something's wrong, which is one more reason to always show one.

#### Colour scheme

The tokens use `light-dark()`, which follows `color-scheme`, so the Radio Group adapts to your light and dark themes on its own.

#### Text size and spacing

Rows have a minimum height in `rem`, and the indicator is sized in `rem` too, so they grow with their text instead of clipping it, at 200% text size ([WCAG 1.4.4](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)) and with wider line, letter and word spacing ([WCAG 1.4.12](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)). A long label wraps beside its indicator rather than under it, so the options stay easy to tell apart.

#### Languages and direction

The Radio Group uses logical properties, so in right-to-left languages its indicators sit on the right, before their labels, without any changes. Remember to translate the legend, the labels, the hint and the error message along with the rest of the page, and to mark any that are in another language with `lang`, so that screen readers pronounce them correctly ([WCAG 3.1.2](https://www.w3.org/WAI/WCAG22/Understanding/language-of-parts.html)).

### Consistent

Once you've learned the [Input](/docs/components/input#consistent)'s API, you already know most of the Radio Group's. These names mean the same thing everywhere in Open Components:

| Name       | Kind | What it means                                                                |
| ---------- | ---- | ---------------------------------------------------------------------------- |
| `size`     | Prop | `xs`, `sm`, `md`, `lg` or `xl`, with the same heights everywhere             |
| `disabled` | Prop | The component can't be used, here the whole group or one radio               |
| `required` | Prop | Its form can't be sent until it has a value                                  |
| `name`     | Prop | The name its form sends its value under                                      |
| `value`    | Prop | The value, which you bind the way your framework binds a form control's      |

We recommend `size="md"` as the default. The Radio Group also leaves a few props out, on purpose:

- There's no `orientation`. Radios stack, for the reasons under [Layout](/docs/components/radio-group#layout), and the arrow keys move both ways whichever way they're laid out.
- There's no `variant` or `color`. A radio has one checked look, from the primary colour, and its one other coloured state, invalid, comes from `aria-invalid`, so its colour and its state can't disagree.
- There's no `options` prop. The radios are children, so each one can have its own label, its own `disabled` and its own attributes, and the code reads like the form it renders.
- The Radio has no `label` prop either. Its content is its label, which also keeps it inside the `<label>` that checks it.

### Type-safe

Props, events and slots are typed, so your editor can autocomplete them and your type checker (`tsc`, `vue-tsc`, `svelte-check`, `ngc` or `astro check`) catches mistakes like a group without a `legend`, which every group needs.

| Radio Group prop | Type                                   | Default | Description                                                                  |
| ---------------- | -------------------------------------- | ------- | ---------------------------------------------------------------------------- |
| `name`           | `string`                               |         | Required. Every radio submits under it, and the hint's and error's IDs start with it |
| `legend`         | `string`                               |         | Required. The question, which names the group                                |
| `hint`           | `string`                               |         | Help that applies to every option, which describes the group                 |
| `error`          | `string`                               |         | What's wrong and how to fix it. While it's set, the group is invalid         |
| `size`           | `"xs" \| "sm" \| "md" \| "lg" \| "xl"` | `"md"`  | How big the radios are                                                       |
| `disabled`       | `boolean`                              | `false` | Disables every radio, and leaves the group out of its form                   |
| `required`       | `boolean`                              | `false` | Makes every radio required, so its form can't be sent without an answer      |
| `value`          | `string`                               |         | The checked radio's value, when you bind it. Without it, the group keeps its own |

| Radio prop | Type      | Default | Description                                                         |
| ---------- | --------- | ------- | ------------------------------------------------------------------- |
| `value`    | `string`  |         | Required. What the group's value is, and its form sends, while this radio is checked |
| `disabled` | `boolean` | `false` | Takes this one option away, while the others stay                    |

| Event    | Payload | Description                                                                 |
| -------- | ------- | --------------------------------------------------------------------------- |
| `change` | `Event` | Fires when people check a radio, from its `<input>`, and bubbles up to the group |

A binding to `value` listens to it for you. The browser doesn't fire `change` on the radio that gets unchecked, so listen on the group, or bind its value, rather than listening to each radio.

| Slot                  | Description                                                          |
| --------------------- | -------------------------------------------------------------------- |
| Radio Group `default` | The radios, one Radio for each option                                |
| Radio `default`       | The label, which names the radio and checks it when pressed          |

### Composable

The Radio Group renders the `<fieldset>`, so everything you pass it that isn't a prop lands there, like a class, an `id` or a listener. A Radio renders two elements, so it splits what you pass between them, as the Input does. Classes and styles go on its root, the `<label>`, so a class can set its variables. Everything else lands on the `<input>`, including ARIA attributes and event listeners, and a ref to the Radio reaches the `<input>` too, since that's what `focus()` needs.

Anything can sit between the radios, like the Input beside Other under [Layout](/docs/components/radio-group#layout), as long as every Radio stays inside its group, which is where it gets its name, its size and its value from.

#### With other components

- An [Input](/docs/components/input) beside a radio, like Other, takes the same `size`, so the two line up.
- A [Button](/docs/components/button) sends the form the group is in. Checking a radio never does, as under [Don't act on change](/docs/components/radio-group#dont-act-on-change).
- The Field, on our [Roadmap](/docs/getting-started/roadmap), labels a single control, like an Input. A group of radios is labelled by its legend instead, which is why the Radio Group renders its own legend, hint and error message, and why they look the way the Field's will.
- A Checkbox, a Switch and a Select, also on our Roadmap, will share the Radio Group's sizes and rules for labels and errors. You'll find when to use each under [FAQ](/docs/components/radio-group#faq).

### Controllable

The Radio Group doesn't keep any state you can't reach. The value is yours to bind, or to leave to the browser, and every other state is a prop that you control:

| State    | How you control it                                                                 |
| -------- | ---------------------------------------------------------------------------------- |
| Value    | `value`, bound to your state, or left to the browser                               |
| Disabled | `disabled` on the group, or on one Radio                                           |
| Required | `required` on the group                                                            |
| Invalid  | `error`, set while there's something to fix (see [Invalid](/docs/components/radio-group#invalid)) |
| Focus    | A ref to a Radio's `<input>`, and `focus()`                                        |

## Agentic Experience (AX)

Finally, let's look at how agents read, fill in and check a radio group. They rely on the same accessibility tree as assistive technologies, and on a contract they can check the code against.

### Semantic

Agents that drive a browser, through Playwright or a browser MCP server, read the page through its accessibility tree, which is made of roles, names, values and states. This is how they see the examples under [States](/docs/components/radio-group#states), in Chrome:

```yaml
- radiogroup "Delivery":
  - text: Delivery
  - radio "Standard" [checked]
  - text: Standard
  - radio "Express"
  - text: Express
- radiogroup "Shipping":
  - text: Shipping
  - radio "Standard" [checked]
  - text: Standard
  - radio "Collect from a store" [disabled]
  - text: Collect from a store
- radiogroup "Plan":
  - text: Plan
  - radio "Personal" [disabled]
  - text: Personal
  - radio "Team" [checked] [disabled]
  - text: Team
- radiogroup "How should we contact you?" [invalid]:
  - text: How should we contact you?
  - paragraph: Choose how we should contact you
  - radio "Email"
  - text: Email
  - radio "Phone"
  - text: Phone
```

The legend names the group, and the group carries `[invalid]`, since it has the `radiogroup` role. A group without a legend is a radio group with no name, so an agent can't tell the delivery options from the payment options, any more than a screen reader user can. With a role and a name, an agent can find the group, and the radio inside it, and check it:

```ts
await page.getByRole("radiogroup", { name: "Delivery" }).getByRole("radio", { name: "Express" }).check();
```

Here's the whole contract in one block, for agents to read before they build or review a radio group:

### Deterministic

The same props always render the same markup, leaving out anything your framework adds for itself, like comments or scoping attributes. For example, here's a required group with a hint, an error and an answer:

```html
<RadioGroup
  name="delivery"
  legend="Delivery"
  hint="Express arrives the next working day"
  error="Choose how you'd like your order delivered"
  required
  value="express"
>
  <Radio value="standard">Standard</Radio>
  <Radio value="express">Express</Radio>
</RadioGroup>
```

And here's what it renders:

```html
<fieldset
  class="radio-group"
  role="radiogroup"
  data-size="md"
  aria-invalid="true"
  aria-describedby="delivery-hint delivery-error"
>
  <legend data-slot="legend">Delivery</legend>
  <p id="delivery-hint" data-slot="hint">Express arrives the next working day</p>
  <p id="delivery-error" data-slot="error">Choose how you'd like your order delivered</p>
  <label class="radio" data-slot="radio" data-size="md">
    <input data-slot="control" type="radio" name="delivery" value="standard" required />
    <span data-slot="label">Standard</span>
  </label>
  <label class="radio" data-slot="radio" data-size="md">
    <input data-slot="control" type="radio" name="delivery" value="express" checked required />
    <span data-slot="label">Express</span>
  </label>
</fieldset>
```

- The size is mirrored as `data-size` on the group and on every radio, and it's always there. The role is always `radiogroup`, so an agent finds every group the same way.
- Parts are marked with `data-slot` and always come in the same order: `legend`, `hint`, `error` and the radios, each with its `control` and `label`. Only the legend and the radios are always there.
- The hint's and error's IDs are the group's `name` with `-hint` and `-error`, so the markup is the same on the server, on the client and in every snapshot. There's nothing random or generated, like IDs or timestamps.
- States change attributes, and the error message comes and goes, but the radios are never replaced, so focus, the checked radio and the screen reader's position all survive every state change, an error included.

### Verifiable

Every rule in the checklist can be checked, and about half of them automatically.

#### Unit tests

Every rule that the checklist checks with a unit test has one in `RadioGroup.test.ts`, which you'll find under [Reference implementation](/docs/components/radio-group#reference-implementation). We run them on every change to this page, so the code you see always passes them.

They run on jsdom, which proves the markup and the behaviour the browser builds on, but not every browser's own keyboard handling. So once you've built your Radio Group, check it with the keyboard in each browser you support: `Tab` and `Shift+Tab` into and out of a group, with and without a checked radio, all four arrow keys, `Space` and a disabled radio.

#### In the browser

In the browser, you can run [axe](https://github.com/dequelabs/axe-core) to check names and contrast, and answer the form the way an agent would, to check what happens when people skip the question:

```ts
import AxeBuilder from "@axe-core/playwright";

test("the checkout asks how to deliver, and says so when it's skipped", async ({ page }) => {
  await page.goto("/checkout");

  const delivery = page.getByRole("radiogroup", { name: "How would you like it delivered?" });
  await page.getByRole("button", { name: "Place order" }).click();

  await expect(delivery).toHaveAttribute("aria-invalid", "true");

    .withTags(["wcag2a", "wcag2aa", "wcag21aa", "wcag22aa"])
    .analyze();
```

## Checklist

Here's every rule in one place, along with where it comes from and how to check it. A radio group meets the standard when it meets every **must**, and each **should** is expected unless you have a good reason not to follow it.

The scope says who meets a rule. **Component** rules are met by the Radio Group itself, so they're the ones to check when you build or review one. **Usage** rules are met by the forms that use it, like asking a question in the legend, so they're the ones to check when you review a screen. **Both** rules need the two to work together, like labelling every radio: the Radio wraps its input in its label, as long as you give it one.

The basis says where a rule comes from. About half the rules rest on **WCAG** 2.2, which we follow at level AA, and name the success criteria behind them, and a few come from **HTML** or the **APG**. The rest are **Open Components** rules, which are our own, like checking a group when people submit rather than as they pass through it. Where a rule goes further than WCAG asks at level AA, its basis says so: some come from level **AAA**, like the 44px rows on touch screens, and a rule that asks for more than its criterion says **beyond**, like using native radios, where WCAG would let you rebuild them by hand.

## Reference implementation

Our Vue 3 reference implementation does its part of every rule on this page, and powers every example on it. It's two components, the Radio Group and the Radio, which reads its name, size, required state and value from the group it's in. Feel free to copy them into your design system and change how they look, but try to keep how they behave. They read the same theme tokens as the Button, so copy [`tokens.css`](/docs/components/button#reference-implementation) from the Button's reference implementation into your theme too.

The tests are in `RadioGroup.test.ts`. To run them, you'll need [Vitest](https://vitest.dev), set to `environment: "jsdom"` and `globals: true`, along with `@testing-library/vue`, `@testing-library/user-event` and `@testing-library/jest-dom`.

```vue [RadioGroup.vue]
<script lang="ts">
import type { InjectionKey } from "vue";

export interface RadioGroupProps {
  /** The name every radio submits its value under. The hint's and error's IDs start with it, so give each group on a page its own. */
  name: string;
  /** Names the group, as its <legend>. Ask the question the radios answer, like "How would you like it delivered?" */
  legend: string;
  /** Help that applies to every option, which screen readers read with the group's name. */
  hint?: string;
  /** What's wrong and how to fix it. While it's set, the group is invalid, and screen readers say so. */
  error?: string;
  size?: "xs" | "sm" | "md" | "lg" | "xl";
  /** Disables every radio, and leaves the group out of its form. */
  disabled?: boolean;
  /** Makes every radio required, so its form can't be sent until one is checked. */
  required?: boolean;
}

/** What the group shares with its radios, which they read from it rather than from props of their own. */
export interface RadioGroupContext {
  readonly name: string;
  readonly size: NonNullable<RadioGroupProps["size"]>;
  readonly required: boolean;
  readonly value: string | undefined;
  select(value: string): void;
}

export const RadioGroupKey: InjectionKey<RadioGroupContext> = Symbol("RadioGroup");
</script>

<script setup lang="ts">
import { onMounted, provide, useTemplateRef } from "vue";

const { name, legend, hint, error, size = "md", disabled = false, required = false } = defineProps<RadioGroupProps>();

/** The checked radio's value, which `v-model` binds. Without it, the group keeps its own, and its form submits it. */
const model = defineModel<string>();

defineSlots<{
  /** The radios, one Radio for each option. */
  default?: () => unknown;
}>();

// Getters, so the radios read the group's props as they are on every render.
provide(RadioGroupKey, {
  get name() {
    return name;
  },
  get size() {
    return size;
  },
  get required() {
    return required;
  },
  get value() {
    return model.value;
  },
  select(value: string) {
    model.value = value;
  },
});

// IDs come from the name rather than being made up, so the markup is the same on the
// server, on the client and in every snapshot.
const describedBy = () => [hint && `${name}-hint`, error && `${name}-error`].filter(Boolean).join(" ") || undefined;

const fieldset = useTemplateRef<HTMLFieldSetElement>("fieldset");

onMounted(() => {
  if (import.meta.env.DEV && !legend.trim()) {
    console.warn("[RadioGroup] has no legend: give it one that asks the question its radios answer.", fieldset.value);
  }
});
</script>

<template>
  <fieldset
    ref="fieldset"
    class="radio-group"
    role="radiogroup"
    :data-size="size"
    :disabled="disabled"
    :aria-invalid="error ? 'true' : undefined"
    :aria-describedby="describedBy()"
  >
    <!-- A fieldset groups the radios and takes its name from its legend. ARIA only supports
         aria-invalid on the radiogroup role, not on a fieldset's own group role or on a
         radio, so the fieldset takes that role, and keeps its legend as its name. -->
    <legend data-slot="legend">{{ legend }}</legend>
    <p v-if="hint" :id="`${name}-hint`" data-slot="hint">{{ hint }}</p>
    <!-- Above the radios, so people read what's wrong before they choose again. -->
    <p v-if="error" :id="`${name}-error`" data-slot="error">{{ error }}</p>
    <slot />
  </fieldset>
</template>
```

```vue [Radio.vue]
import { inject, onMounted, useAttrs, useTemplateRef } from "vue";
import { RadioGroupKey } from "./RadioGroup.vue";

export interface RadioProps {
  /** What the group's `v-model` holds, and its form submits, while this radio is checked. */
  value: string;
  /** Takes this one option away, while the others stay. Arrow keys skip it. */
  disabled?: boolean;
}

// Attributes go on the <input> rather than on the root, so they're declared below.
defineOptions({ inheritAttrs: false });

const { value, disabled = false } = defineProps<RadioProps>();

defineSlots<{
  /** The label, which names the radio and is part of what people can press to check it. */
  default?: () => unknown;
}>();

// The name, size, required state and checked value come from the group, so its radios
// can't disagree on them.
const group = inject(RadioGroupKey, undefined);

const attrs = useAttrs();
// Classes and styles go on the root, which lays out the row, so a class can set its
// variables. Everything else goes on the <input>: `id`, ARIA and listeners. Attrs aren't
// reactive, so these run on every render.
const onRoot = (key: string) => key === "class" || key === "style";
const rootAttrs = () => Object.fromEntries(Object.entries(attrs).filter(([key]) => onRoot(key)));
const controlAttrs = () => Object.fromEntries(Object.entries(attrs).filter(([key]) => !onRoot(key)));

const input = useTemplateRef<HTMLInputElement>("input");

// A ref to the Radio gets you the <input>, through `input`.
defineExpose({ input });

onMounted(() => {
  if (import.meta.env.DEV && !group) {
    console.warn("[Radio] is outside a RadioGroup, so it has no name, legend or value to share: put it in one.", input.value);
  }
});
</script>
```

## FAQ

#### Radio Group or something else?

A Radio Group asks for one answer out of a few, and shows them all. For anything else, another component will do a better job:

| When people need to…                                              | Use                                       |
| ----------------------------------------------------------------- | ----------------------------------------- |
| Pick one option out of a few that fit on the screen               | Radio Group                               |
| Pick one option out of many, like a country                       | Select                                    |
| Pick any number of options, from none to all of them              | Checkbox, in a group                      |
| Agree to one thing, like the terms                                | Checkbox, on its own                      |
| Turn a setting on or off, with an effect they see right away      | Switch                                    |
| Answer yes or no to a question in a form, which is sent later     | Radio Group, with Yes and No              |

A Select hides its options until it's opened, which saves room, but people have to open it to compare them, so we recommend radios whenever the options fit. A Switch acts the moment it's flipped, while a radio's answer waits for its form to be sent. A Checkbox lets people pick more than one, or none, which a radio group can't do once it has an answer. All of them are on our [Roadmap](/docs/getting-started/roadmap), and they'll share the Radio Group's sizes, states and rules for labels and errors.

::accordion
:::accordion-item{label="Why can't people uncheck a radio?"}
Because a radio group is a question with one answer, and browsers don't let people take an answer back to none. If "none" is a real answer, give it a radio of its own, like "None of these" or "I'm not sure", rather than a script that unchecks a radio on a second click, which nobody expects and screen readers don't announce.
:::

:::accordion-item{label="Should a yes or no question be radios or a checkbox?"}
Radios, when people have to answer either way, like "Do you have a passport?". An unticked checkbox can mean no or not answered yet, and only radios can tell the two apart, and make the question required. A single checkbox is the right fit when there's only one thing to say yes to, like agreeing to the terms.
:::

:::accordion-item{label="Why does the Radio Group render its own legend?"}
Because a `<fieldset>` takes its name from the `<legend>` inside it, so the legend can't live anywhere else. The same goes for its hint and error message, which describe the whole group rather than one radio. That's also why the Field, on our [Roadmap](/docs/getting-started/roadmap), won't wrap a Radio Group the way it'll wrap an Input.
:::

:::accordion-item{label="Does the Radio Group work before JavaScript loads?"}
Yes, as far as HTML can take it. The server renders real radios in a real `<fieldset>`, so even before the page hydrates, people can check them with a click or the arrow keys, and their form sends the answer. Only the parts that need JavaScript have to wait for it, which are your bound value and your validation.
:::
